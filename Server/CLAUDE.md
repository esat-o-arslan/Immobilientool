## Architecture

This is a single-page React + TypeScript + Vite app backed by **AWS Amplify Gen 2** (AppSync GraphQL + Cognito + S3).

### File layout

- `src/App.tsx` — **entire frontend** in one ~5 700-line file. Every view component, helper function, and constant lives here. There are no separate component files.
- `src/awsService.ts` — all AWS interactions: GraphQL CRUD (`createAWS`, `updateAWS`, `deleteAWS`, `ladeModellAWS`), bulk data load (`ladeAWSArbeitsdaten`), and the Cognito invite mutation (`erstelleEinladungsauftrag`).
- `amplify/data/resource.ts` — Amplify Gen 2 data schema (15 models, all `allow.authenticated()`).
- `amplify/functions/send-invite/` — Lambda that calls `AdminCreateUser` to invite portal users via Cognito.
- `amplify/backend.ts` — wires auth, data, storage, and the Lambda together.
- `amplify_outputs.json` — auto-generated by Amplify; contains API endpoint, Cognito pool IDs, S3 bucket info. Committed to the repo.

### Data flow

All application data lives in `App`'s `data` state (`Record<string, AnyRecord[]>`). On mount it calls `ladeAWSArbeitsdaten()`, which fetches all 15 models in parallel from AppSync. The result is merged with `seed` (empty arrays + one hardcoded Mitarbeiter entry), so the UI never renders empty unless AWS is completely unreachable.

Writes go through `save(model, item)` in `App`:
1. Optimistic local update via `upsertLocal`.
2. Tries `updateAWS`; falls back to `createAWS` if the update returns empty.
3. On success, syncs the returned record back into state.
4. On failure, reverts or shows `cloudStatus` error message.

Deletes go through `remove(model, id)` with the same optimistic-then-revert pattern.

### GraphQL client

`awsService.ts` builds queries dynamically from the `selections` map (field lists per model) and the `pluralName` from `amplify_outputs.json`'s model introspection. No generated types or codegen—mutations and queries are raw strings.

### Routing / navigation

There is no router library. `view` state in `App` is a discriminated union (`View` type) and each view is rendered inline with `{view === 'xxx' && canAccessView(...) && <Component />}`. `STAFF_NAV` drives the sidebar. Navigation is done with `setView(id)`.

Navigation state (`view`, `selectedPropertyId`, `propertyTab`, etc.) is persisted to `localStorage` under `portal:*` keys so the user's position survives page refreshes.

### Permissions

Rights are strings like `'liegenschaften:lesen'` and `'meldungen:bearbeiten'`. The system is:

- Each `Rolle` has a `rechte` array.
- Each `Mitarbeiter` belongs to a `gruppe` (mapped to a Rolle) and may have `rechteExtra` (additions) and `rechteEntzogen` (removals).
- `effectiveRightsFor(data, employee)` resolves the final set.
- `isAdminEmployee` short-circuits to `['*']` for hardcoded admin emails.
- `VIEW_RIGHTS` maps each `View` to the rights that grant access; `canAccessView` checks them.

### Customer portal vs. staff portal

`mode` state toggles between `'staff'` and `'customer'`. In customer mode the sidebar is hidden and `<CustomerPortal>` is rendered with the selected `KontaktPerson` as context. Staff can switch to customer mode via "Eigentümer-/Mieteransicht wählen" (requires `kundenansicht:oeffnen` right).

Staff can also impersonate another employee (`actingEmployeeId`) for permission previewing without affecting `ownEmployeeId`.

### Key domain models

| Model | Purpose |
|---|---|
| `Liegenschaft` | Properties/buildings |
| `KontaktPerson` | Tenants, owners, contacts linked to a Liegenschaft |
| `Schadenfall` | Damage/service cases with workflow statuses |
| `ChatMessage` | Messages attached to Schadenfall, Liegenschaft, or KontaktPerson |
| `Handwerker` | Contractors |
| `Schluessel` | Key management per property |
| `KalenderTermin` | Calendar entries |
| `Mitarbeiter` | Staff/employees |
| `Rolle` | Role definitions with rights arrays |
| `Einladung` | Cognito invite log |
| `StammdatenAenderung` | Approval workflow for master-data changes |

### Soft-delete convention

Records are never hard-deleted from DynamoDB via the UI. Instead:
- `status` is set to `'Gelöscht'` or `'Archiviert'`.
- The `name` field is prefixed with `[GELÖSCHT]`.
- `cleanDeletedName()` strips that prefix for display; `isNewLocalId(id)` detects local-only records (`tmp-` or `p-` prefix) not yet persisted to AWS.

### File uploads

Done via `aws-amplify/storage` (`uploadData`, `getUrl`). Profile photos go to `profile-images/{employeeId}/`. Documents are stored by URL reference in the model's `dateiUrl` field.
